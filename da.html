1. Lakehouse Architecture & Databricks Platform

Lakehouse Architecture

Definition: Combines data lake (low-cost object storage, open formats) with data warehouse (ACID, schema enforcement, BI support) on a single platform.

  • Data Lake: Cheap storage (S3/ADLS/GCS), any format, schema-on-read
  • Data Warehouse: Structured, schema-on-write, optimized for BI
  • Lakehouse: Open formats + ACID + governance + direct BI access
Exam: Lakehouse eliminates copying data between lake and warehouse. Single source of truth.

Photon Engine ✅ NEW

Definition: Native vectorized C++ query engine that accelerates Spark SQL with better CPU/memory efficiency.

  • Enabled on SQL Warehouses by default
  • Best for scan-heavy, aggregation, and join workloads
  • NOT a storage format or programming language

Auto Loader ✅ NEW

Definition: Incrementally ingests new files from cloud storage (exactly-once semantics).

  • Processes only NEW files as they arrive
  • Supports schema inference and evolution
  • Uses cloudFiles format in Spark
Exam: Auto Loader = file ingestion, NOT loading Python packages or caching queries.

SQL Warehouse vs All-Purpose Cluster

FeatureSQL WarehouseAll-Purpose Cluster
Optimized forSQL/BI queriesAll languages, notebooks, ML
EnginePhoton (vectorized)Standard Spark
ServerlessYes (scale to zero)No
Use caseDashboards, alerts, queriesDevelopment, ML, ETL

Serverless SQL Warehouse & Scale to Zero

Scale to zero: Completely stops with zero cost when idle, restarts in seconds when query arrives.

  • No infrastructure management
  • Best for intermittent, budget-sensitive BI workloads
Exam: "Scale to zero" = NO cost when idle. Not "reduces to one node" or "sends alert".

Warehouse Performance Optimization ✅ NEW

  • 1. Check query profile for bottlenecks first
  • 2. Optimize filters and predicates
  • 3. Consider materializing intermediate results
  • 4. Right-size warehouse (do NOT just upgrade blindly)

2. Unity Catalog & Governance

Unity Catalog Overview

Centralized governance: unified access control, lineage, auditing, data discovery across all assets.

Three-Level Namespace

catalog.schema.object (Table/View/Function/Volume)

SELECT * FROM prod.finance.monthly_report;
Exam: NOT Database→Table→Column. It IS Catalog→Schema→Table/View/Function/Volume.

UC Permissions Model

GrantPurpose
USE CATALOGNavigate into catalog
USE SCHEMANavigate into schema
SELECTRead table/view data
MODIFYWrite/update/delete
CREATE TABLECreate tables in schema
GRANT USE CATALOG ON CATALOG prod TO analysts;
GRANT USE SCHEMA ON SCHEMA prod.finance TO analysts;
GRANT SELECT ON TABLE prod.finance.report TO analysts;
Exam: USE CATALOG alone does NOT grant schema access. Need USE SCHEMA + SELECT.

Principle of Least Privilege ✅ NEW

Users get only minimum permissions needed. Regular access reviews required.

Column Masking / Row Filters

  • Column Masking: Dynamic views or UC column mask using identity-based logic
  • Row Filters: SQL UDFs restricting which rows each user sees
Exam: Single data source serves multiple access levels via identity-based logic.

UC Tags ✅ NEW

Key-value metadata for classification, governance, discovery. Do NOT encrypt or trigger workflows.

External Locations & Volumes ✅ NEW

  • External Location: Registered cloud path with storage credential
  • Volume: Managed/external storage for non-tabular files (governed by UC)

Information Schema ✅ NEW

Permission-aware system views showing only objects the user can access.

SELECT * FROM prod.information_schema.tables WHERE table_schema='finance';

Data Lineage ✅ NEW

Tracks source → transformations → target. Enables root cause analysis and impact analysis.

Delta Sharing ✅ NEW

Open protocol for secure cross-org data sharing without copying. Works with pandas/Spark/Power BI.

Dashboard Security ✅ NEW

Queries execute under viewer's identity. UC policies (row filters, masks) apply per viewer.

Exam: Uses VIEWER identity (credential passthrough), not owner.

3. Delta Lake

Delta Lake Overview

Open-source storage layer: ACID transactions + scalable metadata + time travel on data lakes.

  • Built on Parquet + JSON transaction log (_delta_log)
  • Schema enforcement and evolution
  • Unified batch and streaming

Managed vs External Tables

ManagedExternal
StorageMetastore-controlledUser-specified LOCATION
DROPDeletes metadata + data filesDeletes metadata only, files remain
Exam: DROP managed = data GONE. DROP external = metadata removed, files remain.

Time Travel

SELECT * FROM t VERSION AS OF 5;
SELECT * FROM t TIMESTAMP AS OF '2024-01-15';

Query historical snapshots for comparison, audit, rollback.

Exam: Time Travel is NOT VACUUM, NOT OPTIMIZE, NOT ANALYZE TABLE.

DESCRIBE HISTORY (Audit)

DESCRIBE HISTORY catalog.schema.table;

Shows version, timestamp, userId, operation for each commit.

Exam: DESCRIBE HISTORY = audit tool. NOT DESCRIBE TABLE EXTENDED, NOT SHOW GRANTS.

OPTIMIZE & ZORDER

OPTIMIZE my_table ZORDER BY (region, date);
  • OPTIMIZE: compacts small files into larger ones
  • ZORDER: co-locates data for better data skipping
  • Best on low-to-medium cardinality filter columns
Exam: ZORDER on very high-cardinality = LESS effective. Run after many writes.

VACUUM

VACUUM my_table RETAIN 168 HOURS; -- default 7 days

Removes old unreferenced files. Short retention breaks time travel!

Exam: VACUUM ≠ OPTIMIZE (compress). Short retention = risk breaking concurrent reads.

Liquid Clustering ✅ NEW

Replaces partition + ZORDER. Automatically reorganizes data; can change clustering keys without full rewrite.

Change Data Feed (CDF) ✅ NEW

Records row-level changes (insert/update_preimage/update_postimage/delete) for incremental ETL.

📦 Family: Delta Lake Operations

OPTIMIZE vs VACUUM vs ANALYZE — often confused:

CommandPurposeChanges Data?Performance Effect
OPTIMIZECompact small files → largerNo (same data, better layout)Faster reads (fewer files)
VACUUMDelete old unreferenced filesNo (current version unchanged)Saves storage; may break time travel
ANALYZE TABLECompute column statisticsNoBetter optimizer decisions
DESCRIBE HISTORYShow commit audit logNoNone (read-only metadata)
RESTORERollback to prior versionYes (reverts data!)None
Exam trap: OPTIMIZE ≠ VACUUM. OPTIMIZE restructures. VACUUM deletes old files. Neither changes actual rows.

📦 Family: Table Data Organization

Partitioning vs ZORDER vs Liquid Clustering:

StrategyMechanismBest ForLimitation
PartitioningSeparate directories per valueLow-cardinality (date, region)Too many → small file problem
ZORDERCo-locate related valuesMedium-cardinality WHERE colsHigh-cardinality = poor co-location

Exam trap: Partitioning on user_id (high card) = millions of tiny files. Use ZORDER or Liquid Clustering instead.

5. SQL Fundamentals

SQL Execution Order

FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
  • WHERE: before aggregation (no aggregate functions allowed)
  • HAVING: after aggregation (aggregate functions OK)
Exam: WHERE SUM(x)>100 = ERROR. Use HAVING SUM(x)>100.

COUNT(*) vs COUNT(col) vs COUNT(DISTINCT col)

ExpressionBehavior
COUNT(*)ALL rows regardless of NULLs
COUNT(col)Non-NULL values only
COUNT(DISTINCT col)Unique non-NULL values

NULL Handling

  • AVG/SUM/COUNT(col) — skip NULLs silently
  • COUNT(*) — includes all rows
  • NULL in arithmetic → NULL propagates
  • NULL = NULL → UNKNOWN (use IS NULL)
Exam: AVG does NOT replace NULL with 0. It SKIPS them entirely.

COALESCE ✅ NEW

Returns first non-NULL argument left-to-right. COALESCE(a,b,c) — if a=NULL,b=NULL,c=5 → returns 5.

CASE WHEN

Evaluates top-down, stops at first TRUE. Order is critical — narrower conditions first!

Exam: Broad threshold first swallows narrower categories.

GROUP BY ALL ✅ NEW

Auto-groups by every non-aggregate column in SELECT.

SELECT region, product, SUM(sales) FROM t GROUP BY ALL;

GROUPING SETS ✅ NEW

Multiple aggregation levels in one pass: detail + subtotals + grand total.

GROUP BY GROUPING SETS ((region,product), (region), ())

Set Operations

OpBehavior
UNION ALLAll rows including duplicates
UNIONRemoves duplicates
INTERSECTRows in BOTH sets
EXCEPTRows in first NOT in second (distinct)
Exam: Reconciliation = UNION ALL. EXCEPT returns DISTINCT rows.

MERGE (Upsert) ✅ NEW

MERGE INTO target USING source ON target.id = source.id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;
Exam: Multiple matches = error/non-deterministic. Ensure unique ON condition.

Correlated vs Uncorrelated Subquery ✅ NEW

  • Uncorrelated: Executes once independently
  • Correlated: References outer columns; re-evaluated per outer row

CTE (Common Table Expression) ✅ NEW

WITH monthly AS (SELECT month, SUM(rev) total FROM sales GROUP BY month)
SELECT * FROM monthly WHERE total > 1000000;

Improves readability, enables recursion, query-scoped only.

Recursive CTE ✅ NEW

Anchor member (base) + Recursive member (references CTE). Iterates until no new rows.

WITH RECURSIVE tree AS (
  SELECT * FROM emp WHERE mgr IS NULL  -- anchor
  UNION ALL
  SELECT e.* FROM emp e JOIN tree t ON e.mgr=t.id  -- recursive
) SELECT * FROM tree;

EXISTS vs IN ✅ NEW

  • EXISTS short-circuits after first match (efficient for large correlated checks)
  • IN evaluates all values and has different NULL semantics
  • NOT IN + NULLs in subquery = wrong/empty results

TABLESAMPLE ✅ NEW

SELECT * FROM big_table TABLESAMPLE (10 PERCENT);
SELECT * FROM big_table TABLESAMPLE (1000 ROWS);

Quick exploration without full table scan.

EXPLAIN ✅ NEW

Shows query execution plan without running it. Reveals joins, scans, filter pushdown.

EXPLAIN EXTENDED SELECT * FROM t WHERE region='US';

6. Joins

Join Types

One-to-Many Fan-out Problem

Joining fact to detail with duplicate keys inflates SUM/COUNT.

Exam: Always check join key uniqueness. Aggregate before join or deduplicate.

LEFT JOIN More Rows Than Left Table ✅ NEW

Cause: duplicate join keys in RIGHT table. Each left row matches multiple right rows.

Anti Join: NOT EXISTS vs NOT IN

  • NOT IN + NULLs in subquery = empty/wrong result
  • Use NOT EXISTS or LEFT ANTI JOIN (NULL-safe)

Semi Join ✅ NEW

WHERE id IN (SELECT...) optimized as LEFT SEMI JOIN. EXISTS short-circuits after one match.

Broadcast Join ✅ NEW

Broadcast small dimension to avoid expensive shuffle of large fact table.

SELECT /*+ BROADCAST(dim) */ * FROM fact JOIN dim ON ...
Exam: BroadcastHashJoin eliminates shuffle. Use for small dimension (~10MB).

Lateral Join ✅ NEW

Right-side subquery can reference left-side columns. Useful for top-N per group and row-generating functions.

📦 Family: Join Performance Strategies

StrategyMechanismWhen UsedCost
BroadcastHashJoinSmall table sent to all nodesOne side < ~10MBLow (no shuffle of large table)
SortMergeJoinBoth shuffled + sortedBoth tables largeHigh (full shuffle both sides)
ShuffleHashJoinHash on key + shuffleOne side smaller (but >broadcast)Medium
-- Force broadcast when optimizer misses small table
SELECT /*+ BROADCAST(dim) */ * FROM fact_1B JOIN dim_20MB ON ...
Exam trap: SortMergeJoin for 20MB dim + 1B fact = bad. Hint BROADCAST to eliminate expensive shuffle.

7. Window Functions

Window Function Syntax

function() OVER (
  PARTITION BY group_col
  ORDER BY sort_col
  ROWS/RANGE frame_spec
)

ROW_NUMBER vs RANK vs DENSE_RANK

FunctionTies (10,20,20,30)
ROW_NUMBER()1, 2, 3, 4 (unique)
RANK()1, 2, 2, 4 (gaps)
DENSE_RANK()1, 2, 2, 3 (no gaps)
Exam: ROW_NUMBER for latest-per-group. RANK for competition. DENSE_RANK for top-N values.

LAG / LEAD ✅ NEW

revenue - LAG(revenue,1) OVER (ORDER BY month) AS mom_change
  • LAG = previous row value; LEAD = next row value
  • First row: LAG returns NULL (not zero, not error)
  • 3rd argument = custom default: LAG(rev,1,0)

Running Total / Cumulative Sum

SUM(amt) OVER (PARTITION BY region, year ORDER BY month
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
Exam: Partition by BOTH region AND year to reset at each year boundary.

ROWS vs RANGE ✅ NEW

  • ROWS: Physical positions (exact row count)
  • RANGE: Logical value-based (peers with same value treated equally)
Exam: ROWS = positional. RANGE = value-based. NOT interchangeable.

QUALIFY ✅ NEW

Filters window function results directly without subquery wrapper.

SELECT * FROM orders
QUALIFY ROW_NUMBER() OVER (PARTITION BY cust ORDER BY dt DESC) = 1;
Exam: QUALIFY ≠ HAVING. It filters on window results. No CTE/subquery needed.

Top-N Per Group ✅ NEW

ROW_NUMBER/RANK + PARTITION BY + ORDER BY + filter rank <= N.

Exam: Standard pattern for top-N per group (not LIMIT, not TABLESAMPLE).

Gap Detection with LEAD ✅ NEW

SELECT id, LEAD(id) OVER (ORDER BY id) as next_id
FROM orders
HAVING next_id - id > 1; -- gaps exist here

9. Performance Optimization

Partition Pruning ✅ NEW

Engine skips entire partitions not matching filter predicates. Dramatically reduces data scanned.

Exam: Filter on partition column = huge speedup (reads only relevant partitions).

ZORDER Effectiveness ✅ NEW

  • Best on low-to-medium cardinality columns used in WHERE
  • Very high cardinality = less co-location benefit
  • Choose columns frequently filtered, not all columns

Broadcast Join

Small table (<10MB) broadcast to all nodes avoids shuffle of large table.

Incremental Processing ✅ NEW

Filter on date column to process only new/changed records since last run.

Exam: Avoid re-scanning entire history daily. Use WHERE date >= last_run_date.

Query Profile ✅ NEW

Diagnose slow queries: check for full scans, missing filters, unnecessary shuffles, spills.

Idempotent Pipelines ✅ NEW

Produce same output regardless of how many times they run. Critical for safe retries.

10. Dashboards, Alerts & Parameters

Query Parameters

Input controls passing dynamic values (date, region) into dashboard queries without editing SQL.

SELECT * FROM sales WHERE region = :region AND date >= :start_date;
Exam: Parameters let business users filter interactively without touching SQL.

SQL Alerts

Scheduled queries + threshold conditions + notification destinations (email/Slack).

  • Create query that returns a value
  • Set condition (value drops below X)
  • Set schedule (e.g., every hour)
  • Configure notification destination
Exam: SQL Alert = scheduled query + threshold + notification. Not custom SMTP scripts.

Dashboard Refresh / Stale Data ✅ NEW

Stale data at 9AM? Likely cause: dashboard refresh schedule runs BEFORE ETL completes.

Exam: Fix by scheduling dashboard refresh AFTER ETL job finishes, not before.

Debugging Zero-Row Results ✅ NEW

Remove filters one at a time. Verify filter values actually exist in data.

12. Data Quality

Six Data Quality Dimensions

DimensionQuestionExample Violation
AccuracyIs data correct?Wrong address
CompletenessIs all data present?Missing phone numbers
ConsistencySame across systems?Balance mismatch between reports
TimelinessAvailable on time?Data arrives 2hrs after SLA
UniquenessNo duplicates?Same customer_id appears twice
ValidityConforms to rules?Email without @ symbol
Exam: Dashboard total ≠ source total = Consistency. Late data = Timeliness. Duplicate PK = Uniqueness.

Detecting Duplicates ✅ NEW

-- Detect
SELECT key, COUNT(*) FROM t GROUP BY key HAVING COUNT(*) > 1;
-- Remove (keep latest)
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated DESC) rn
  FROM t
) WHERE rn = 1;

Data Profiling ✅ NEW

Systematically examine: distributions, null rates, cardinality, outliers, data types, value ranges, join keys.

Exam: ALWAYS profile before analysis. Not just first 5 rows or row count.

Data Contracts ✅ NEW

Formal agreement: schema spec, freshness SLA, null guarantees, quality rules, breaking change process.

Shifts quality responsibility to producers. Consumers can trust and depend on the data.

Data Freshness SLA ✅ NEW

Commitment that data updated by specific time. Monitor: compare last-modified timestamp vs deadline.

NULL Handling Best Practice ✅ NEW

Understand what NULL represents in context (unknown vs not-applicable vs missing). Never ignore silently.

  • Use COALESCE/IFNULL for explicit handling
  • NULL propagates in arithmetic
  • COUNT(col) excludes NULLs; COUNT(*) includes all

Data Validation After Load ✅ NEW

Compare row counts + key aggregate totals (SUM, DISTINCT counts) between source and target.

Expectations (DLT/SDP) ✅ NEW

Declarative EXPECT rules validating incoming data. Can warn, drop invalid rows, or fail pipeline.

PII Handling ✅ NEW

Discover unmasked PII → Report to governance team immediately. Do NOT use, share, or unilaterally delete.

13. Analytical Methods

Cohort Analysis ✅ NEW

Group users by shared characteristic (e.g., signup month) and track behavior over time.

Reveals lifecycle patterns, retention curves, behavioral shifts.

RFM Analysis ✅ NEW

Recency, Frequency, Monetary — segments customers by purchase behavior.

  • Recency: how recently they purchased
  • Frequency: how often they purchase
  • Monetary: how much they spend

Identifies high-value and at-risk customer groups.

Funnel Analysis ✅ NEW

Shows step-by-step drop-off rates. Pinpoints exactly WHERE in process users are lost.

Exam: Funnel shows WHICH step loses users. Simple conversion rate only shows final number.

Pareto (80/20) Analysis ✅ NEW

Identifies vital few contributors (e.g., 20% of customers generating 80% of revenue).

Focus resources on high-impact segments.

Seasonality ✅ NEW

Regular repeating patterns at fixed intervals (daily/weekly/yearly).

Exam: Ignoring seasonality → false anomaly alerts and incorrect trend interpretation.

Outlier Handling ✅ NEW

14. ML & Statistics Fundamentals

Precision vs Recall ✅ NEW

MetricFocusPrioritize When
PrecisionOf predicted positives, how many correct?False positives costly (spam filter)
RecallOf actual positives, how many caught?False negatives costly (fraud detection)
Exam: Fraud = prioritize RECALL (catch all fraud, accept some false alarms).

Accuracy Trap (Imbalanced Data) ✅ NEW

99.7% accuracy with 0.3% fraud rate = model predicts majority class for everything, catches zero fraud.

Exam: High accuracy ≠ good model when classes are imbalanced. Use precision/recall/F1/AUC.

Overfitting ✅ NEW

High training score + much lower test score = model memorized noise, doesn't generalize.

98% train, 72% test = classic overfitting signal.

Data Leakage ✅ NEW

Using future information or target-correlated features unavailable at prediction time.

  • Inflates metrics artificially
  • Model fails in production
  • Fix: split first, preprocess separately

Distribution Shift ✅ NEW

Old test set (2022) may not represent current production (2026). Behavior/policies change over time.

Exam: Test data must share same distribution as production for metrics to be reliable.

Stratified Sampling ✅ NEW

For rare events (0.01% fraud), random sampling yields too few cases. Stratified sampling preserves class proportions.

Survivorship Bias ✅ NEW

Analyzing only surviving/successful cases while missing failures. Skews conclusions optimistically.

Fix: Include full population at starting point.

Fact table (measures) surrounded by dimension tables (descriptive attributes). Optimized for analytics.

17. PySpark Essentials ✅ NEW

Transformations vs Actions

  • Transformations (lazy): filter, select, join, withColumn — build execution plan
  • Actions (trigger execution): count, collect, show, write — materialize results

select() vs withColumn()

  • select('a','b',expr) — returns only specified columns
  • withColumn('new',expr) — returns ALL columns + new/replaced one

repartition() vs coalesce()

  • repartition(N) — full shuffle (increase or decrease partitions)
  • coalesce(N) — reduces partitions without full shuffle (cheaper)

cache() / persist()

Store DataFrame in memory to avoid recomputation when reused multiple times. Unpersist when done.

Write to Delta

df.write.format('delta').mode('overwrite').saveAsTable('catalog.schema.table')

Modes: overwrite, append, ignore, error.
